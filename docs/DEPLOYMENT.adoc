= Deployment
:toc: left
:icons: font

Bookie's web app runs on Azure App Service (`bookie-knowall` in resource group `ka-bookie-prod`,
https://bookie.knowall.ai). This page covers the checks every change goes through, how a release
reaches production, and the one-off setup the release workflow needs. The agent's VM is deployed
separately; see `agent/README.md`.

== Continuous integration

`.github/workflows/ci.yml` runs on every pull request and every push to `main`:

[cols="1,3"]
|===
| Job | What

| Format, lint, typecheck, unit tests
| `format:check`, `lint`, `typecheck`, then `bun run test:coverage` (vitest with V8 coverage). The
  job summary shows a coverage table and the `coverage-summary` artifact holds
  `coverage-summary.json`.
| Production build
| `bun run build`.
| End-to-end
| Playwright against the fictional demo organisations, as a matrix over the `desktop` and `mobile`
  projects (`web/playwright.config.ts`; `mobile` runs the `@mobile` specs on a Pixel 7). On failure
  the HTML report is uploaded as `playwright-report-<project>`.
| Secret scan
| gitleaks over the full history, with `.gitleaks.toml`.
|===

`.github/workflows/pr-lint.yml` checks the pull request itself, with the same rules as Thyme and
ZapDesk: a conventional-commit title (`feat:`, `fix:`, `perf:`, `refactor:`, `chore:`, `ci:`,
`docs:`, `deps:`, `test:`, `build:`, `style:`; no scope), a `Fixes #nnn` line for
`feat`/`fix`/`perf`/`refactor`, and a non-empty `## Test plan`.

`.github/workflows/bc-extension.yml` compiles the optional Business Central extension when
`bc-extension/` changes.

=== Coverage thresholds

The thresholds live in `web/vitest.config.ts`, a little below the measured coverage, so a change
that drops coverage fails CI. Run `bun run test:coverage` in `web/` to see the numbers locally
(HTML report in `web/coverage/`). Raise the thresholds when coverage grows.

== Releasing to production

Push a version tag from `main`:

[source,bash]
----
git checkout main && git pull
git tag v1.2.3
git push origin v1.2.3
----

`.github/workflows/deploy-production.yml` then:

. runs format, lint, typecheck and unit tests on the tagged commit;
. signs in to Azure with OpenID Connect (no stored password);
. runs `infra/web/deploy.sh <sha>`: a clean worktree build of the tagged commit, a zip of the Next
  standalone output, `az webapp deploy --clean true`, and a wait until the live site serves the new
  `BUILD_ID`.

The deploy job runs in the `production` GitHub environment, and only one production deploy runs at
a time (later ones queue rather than cancel). To redeploy without a new tag, run the workflow from
the *Actions* tab (*Run workflow*); it deploys the commit of the branch or tag you pick.

=== Deploying from a workstation

The same script works locally, signed in with `az login`:

[source,bash]
----
infra/web/deploy.sh            # origin/main
infra/web/deploy.sh v1.2.3     # any git ref
----

It builds from a clean worktree, so no local `.env` file can end up in the bundle. `APP`, `RG`,
`PUBLIC_URL` and `AGENT_UPN` override the defaults.

=== App settings

The workflow deploys code only. Runtime settings (`NEXTAUTH_SECRET`, `AZURE_AD_*`,
`BOOKIE_CONFIG_KEY`, Azure OpenAI and so on; see `web/.env.example`) are App Service application
settings, mostly Key Vault references, and are managed in Azure, not in GitHub.

== One-off setup for the release workflow

These live outside the repository. Never put their values in a workflow file: the repository is
public.

. *An identity for GitHub Actions.* An Entra app registration (or user-assigned managed identity)
  with a *federated credential* for this repository's `production` environment: issuer
  `https://token.actions.githubusercontent.com`, subject
  `repo:knowall-ai/bookie:environment:production`, audience `api://AzureADTokenExchange`.
. *Its permission.* The *Website Contributor* role on the `bookie-knowall` App Service (enough for
  `az webapp deploy`).
. *Repository secrets* (Settings > Secrets and variables > Actions):
+
[cols="1,3"]
|===
| Secret | Value

| `AZURE_CLIENT_ID` | the identity's client (application) id
| `AZURE_TENANT_ID` | its Entra tenant id
| `AZURE_SUBSCRIPTION_ID` | the subscription holding `ka-bookie-prod`
|===
. *The `production` environment* (Settings > Environments). Add a deployment rule that allows only
  `v*` tags (and `main`, if manual runs from `main` are wanted), and optionally required reviewers.
  The federated credential above only works for jobs in this environment.

== Sign-in app registration

Sign-in uses a multi-tenant Entra app registration. Its redirect URI is
`<site URL>/api/auth/callback/azure-ad` (`http://localhost:3103/api/auth/callback/azure-ad` in
development), plus one per guest host tenant as described in `docs/ACCESS.adoc`. Put its client id
and secret in `AZURE_AD_CLIENT_ID` and `AZURE_AD_CLIENT_SECRET` (`web/.env.local` in development,
App Service settings in production).
