= Bitcoin wallets as bank accounts
:toc: left
:icons: font

Bookie can show a Bitcoin wallet as a bank account whose statement is the blockchain. The wallet's
extended public key (xpub) or output descriptor tells Bookie which addresses belong to it; Bookie reads
their transactions live from an Electrum server and shows them under *Accounting › Bank accounts*,
valued in the organisation's own currency at the Kraken price at each transaction's own time.

Bookie is *watch-only*: an xpub or descriptor can see a wallet but never spend from it. Bookie, and the
Business Central extension below, refuse private keys (xprv, yprv, zprv and their testnet forms).

== Where the descriptor lives

[cols="1,3", options="header"]
|===
| Organisation | Where you enter the wallet

| Business Central
| On the *bank account* in Business Central, with the *Bookie Bitcoin* extension (below). Every bank
  account with a descriptor is a wallet in Bookie; there is no Bookie setting for it. The descriptor
  stays in your own Business Central and Bookie reads it live, like the rest of your books.

| Other organisations
| *Settings › Bitcoin wallets* in Bookie (members only). The descriptor is sealed with your tenant's
  key and stored in your own SharePoint (the `BookieConnections` list, record `bitcoin-wallet:{id}`),
  like Xero connection secrets, and never shown again.
|===

Either way, the descriptor never reaches the browser: pages show the wallet's name, script type and
bank account number only.

== Business Central: the Bookie Bitcoin extension

A small per-tenant extension, `bc-extension-bitcoin/` in this repository, separate from the Bookie BC
API extension so either can be installed alone.

[cols="1,3"]
|===
| App | `Bookie Bitcoin` by `KnowAll`, id `b43701b1-70d6-43d4-9d83-3a9a6dc6a208`, BC 27.0 or later, cloud
| Object ids | 50250 to 50299 (the Bookie BC API extension uses 50200 to 50249 and Thyme 50100 to 50199, so all three can be installed together)
| Table | *Bookie BTC Wallet*: one row per bank account (`Bank Account No.`) with `Bitcoin Wallet Descriptor` (Text[1024]) and `Bitcoin Script Type` (Automatic, WPKH, SHWPKH, TR, WSHMulti, PKH). It is a table of its own, not fields on Bank Account, so reading it takes `BOOKIE BTC READ`: Bank Account rights alone (personalisation, Edit in Excel, OData, reports) never reach the descriptor. Entering a private key is refused. Deleting the bank account deletes its wallet row.
| Page extension | *Bank Account Card*: a *Bitcoin Wallet* group that reads and writes that table, shown only to users who can read it (`BOOKIE BTC READ` or `EDIT`), editable only with `BOOKIE BTC EDIT`. Clearing the descriptor removes the wallet.
| API page | `api/bookie/bitcoin/v1.0/companies({id})/bitcoinWallets`, read-only: `bankAccountId` (the same SystemId as API v2.0 bankAccounts), no., name, currency code, descriptor, script type
| Permission sets | `BOOKIE BTC READ` (see wallets; run the API page), `BOOKIE BTC EDIT` (also enter and change them)
|===

When Bookie gets a 404 from the API page it says the extension isn't installed; a 403 means the
signed-in user hasn't got `BOOKIE BTC READ`. Either way the Bank accounts page says so and links here.

=== Build

CI (`.github/workflows/bc-extension.yml`) compiles it with the other extension on every PR that
touches either folder (CodeCop, PerTenantExtensionCop and UICop, warnings as errors) and uploads it
as the `bookie-bitcoin-bc-extension` artifact. Locally:

[source,bash]
----
dotnet tool install --global Microsoft.Dynamics.BusinessCentral.Development.Tools --version 18.1.43.24897
bc-extension-bitcoin/build.sh                  # symbols from the public feed, `al` tool
SYMBOLS=sandbox bc-extension-bitcoin/build.sh  # symbols from your Sandbox (az login), `al` tool
ALC_DLL=~/.vscode/extensions/ms-dynamics-smb.al-*/bin/alc.dll bc-extension-bitcoin/build.sh  # another alc
# -> bc-extension-bitcoin/output/KnowAll_Bookie Bitcoin_1.0.0.0.app
----

Or open `bc-extension-bitcoin/` in VS Code with the AL Language extension, run *AL: Download
Symbols* against a sandbox and build with Ctrl+Shift+B. AL-Go for GitHub works too: point a project
at `bc-extension-bitcoin`.

=== Publish

You need `EXTEN. MGT. - ADMIN` (or `SUPER`). Sandbox first, then Production with the same `.app`.

. In Business Central, search *Extension Management*, choose *Manage › Upload Extension*.
. Choose the `.app`, *Deploy to: Current version*, accept, *Deploy*.
. *Manage › Deployment Status* shows *Completed*; *Bookie Bitcoin* appears under Installed Extensions.

To update, raise `version` in `bc-extension-bitcoin/app.json` and upload again. Uninstalling with
*Delete Extension Data* removes the descriptors from your bank accounts.

=== Assign the permission sets

[cols="1,3", options="header"]
|===
| Who | Permission set

| People who use Bookie with this company and should see its wallets | `BOOKIE BTC READ`
| People who enter or change a wallet descriptor | `BOOKIE BTC EDIT` (it grants nothing on Bank Account itself; opening the card still needs their usual sets)
| The Bookie agent's service-to-service app (*Microsoft Entra Applications* › `Bookie Business Central` › *User Permission Sets*) | `BOOKIE BTC READ` only, never EDIT
|===

Search *Users* (or *Security Groups*, recommended, linked to an Entra group such as "Bookie users"),
open the user or group and add the permission set. Leave *Company* blank for every company, or pick one.
The descriptor reveals every address and balance of the wallet, so give `BOOKIE BTC READ` only to people
who may see the wallet's history.

=== Set up the BTC currency and bank account

. *Currencies*: add `BTC` (Bitcoin) with *Amount Rounding Precision* and *Unit-Amount Rounding
  Precision* `0.00000001` and *Amount Decimal Places* and *Unit-Amount Decimal Places* `8:8`, and its
  realised and unrealised gains and losses accounts. Business Central converts BTC to your local
  currency with the rates you enter under *Currency Exchange Rates*; Bookie doesn't enter them.
. *Bank Account Posting Groups*: a group whose G/L account is where you hold digital assets.
. *Bank Accounts*: a new account, for example `BTC-01` "Treasury wallet", *Currency Code* `BTC`, that
  posting group.
. On its card, in *Bitcoin Wallet*, paste the wallet's zpub, ypub, xpub or output descriptor. For a
  bare xpub choose the *Bitcoin Script Type* your wallet uses; leave it on *Automatic* otherwise.

Bookie shows the wallet under Bank accounts straight away. It flags a wallet whose bank account
currency isn't `BTC`, and shows a descriptor it can't use with the reason rather than failing the page.

== What Bookie accepts

[cols="1,2,2", options="header"]
|===
| Input | Addresses | Chains scanned

| `zpub...` (`vpub` on testnet) | Native SegWit, P2WPKH (`bc1q...`) | receive `/0/*`, change `/1/*`
| `ypub...` (`upub`) | Nested SegWit, P2SH-P2WPKH (`3...`) | receive `/0/*`, change `/1/*`
| `xpub...` (`tpub`) + script type | Whichever type you choose | receive `/0/*`, change `/1/*`
| `pkh(KEY)` | Legacy P2PKH (`1...`) | as the descriptor says
| `wpkh(KEY)` | P2WPKH | as the descriptor says
| `sh(wpkh(KEY))` | P2SH-P2WPKH | as the descriptor says
| `tr(KEY)` | Taproot key path only (BIP86) | as the descriptor says
| `wsh(multi(k,KEY,...))`, `wsh(sortedmulti(k,KEY,...))` | P2WSH multisig, up to 20 keys | as the descriptor says
|===

`KEY` is `[fingerprint/origin/path]xpub.../<0;1>/*`. The key origin is optional; the path after the
xpub must be non-hardened and end in `/*`. `<0;1>` gives the receive and change chains; a descriptor
with a single chain (for example `/0/*`) scans that chain only, and the wallet page says change
addresses aren't included. A `#checksum` (BIP380) is checked when present. Taproot script trees,
`sh(multi)` and Miniscript aren't supported yet.

== Reading the chain

For each chain, Bookie derives addresses until it finds 20 unused ones in a row (the gap limit), and
asks the Electrum server for each address's history (`blockchain.scripthash.get_history`) and balance
(`blockchain.scripthash.get_balance`). It then fetches every transaction
(`blockchain.transaction.get`) and the header of every block they are in (`blockchain.block.header`)
for the block time.

Per transaction Bookie shows:

* the txid, the date of its block (UTC) and its confirmations;
* the amount: what was paid to the wallet's own addresses minus what it spent from them;
* the fee, only when the wallet funded every input, so the whole fee is the wallet's. A receipt's fee
  was paid by the sender, and a jointly funded transaction (payjoin, coinjoin) has no fee shown, with
  that reason: Bookie doesn't guess the wallet's share. A wallet with more than 10,000 transactions
  isn't read live; the page says so.

A transaction the server reports at height 0 or below is in the mempool: it is shown as *Pending*,
counted in the *Pending* balance, never in the confirmed balance, and has no value in fiat.

*Stateless.* Bookie keeps no chain data. The only cache is in memory, for five minutes, keyed by the
Entra tenant id, the organisation, the wallet and its descriptor's checksum (so a descriptor changed in
Business Central is never served stale).

== The balance panel

Each wallet's card on the Bank accounts page, and the top of its own page, shows:

* the *confirmed balance*, with pending transactions apart ("pending, unconfirmed, not settled");
* a *BTC | <base currency>* toggle (for example *BTC | GBP* or *BTC | USD*). BTC shows the exact
  amounts. The currency view shows the balance at Kraken's latest price, labelled with its source and
  time, or "—" with the reason. The choice is remembered per person in the browser (`localStorage`), not
  on the server, and every wallet on screen follows it;
* a *balance-over-time chart*: 30 days on the card, 90 days on the wallet page. The BTC line is exact,
  the confirmed balance at the end of each UTC day, worked back from the chain history; pending
  transactions are in no day. In the currency view each day is valued at Kraken's daily close for that
  date (today at the last trade), and the source is labelled. Days without a price are left out;
* *Last checked*: when Bookie last read the wallet from Electrum, and the block height it read at.

== Values in the organisation's currency ("worth at the time")

Each figure is in the organisation's *base currency*, as its books report it (Business Central's local
currency, Xero's base currency). Prices come only from Kraken's public market data, using the pair for
that currency: `XBTGBP`, `XBTUSD`, `XBTEUR`, or any other pair Kraken lists. If Kraken has no pair for
the currency, or the books don't say what the base currency is, the value is "—" with the reason. Bookie
never converts through another currency.

Payments are usually worked out in sats at the moment of payment, so each transaction is valued at
*its own time*:

[cols="1,3", options="header"]
|===
| Situation | Rate used, and its label

| A confirmed transaction | The Kraken trade nearest the second its block was mined (`Trades?since=`, Kraken's full trade history): *Kraken XBTUSD at 14:32 UTC, 10 Oct 2026*
| The trade can't be looked up (rate limit) or none was within six hours | The Kraken daily close of the block's UTC day, closed days only (`OHLC?interval=1440`, about 720 days), labelled *(fallback: the price at the block time wasn't available)*
| The confirmed balance | *Kraken XBTUSD last trade at 09:15 UTC, ...*
| A pending transaction | None: "—". Electrum doesn't report when a transaction was first seen, so there's no time to price it at.
| Kraken unreachable, or no price at all | None: "—" with the reason
|===

Bookie never values an old amount at today's price. To stay within Kraken's public rate limits it makes
at most twelve trade lookups per page view. Other transactions on that page get the labelled daily-close
fallback until they're looked up on a later view. Exact-time prices are cached for the life of the
process, so a page fills in as it's revisited. Kraken prices are public data, not anyone's books.

*These values are for information only.* They show what a transaction was worth at the time. They are
not what Business Central posts: Business Central converts BTC at its own exchange rate, one per day.
Wallet apps, Kraken and Business Central all use different rates, so the figures never match exactly.
Matching a wallet to the books is therefore exact on the Bitcoin side only: txid and satoshis.

== Reconciling against Business Central

A wallet in a Business Central company is its BTC bank account, so its page has a *Reconcile* tab
that compares the chain with that account's posted bank ledger entries. Bookie needs both extensions:
*Bookie Bitcoin* (which bank accounts are wallets) and the *Bookie BC API* extension (`bc-extension/`,
for the bank account ledger entries, which API v2.0 doesn't publish). The bank account's currency must
be `BTC`: an account in another currency can't be compared with chain amounts, and the tab says so.

=== Matching

. *By txid.* A ledger entry whose *External Document No.* is the start of the txid (Business Central
  keeps 35 characters and upper-cases them), or whose *Description* contains the full txid. Every
  entry for the same txid is grouped. If their total isn't the chain amount, the match is flagged
  *Amounts differ*.
. *By exact amount*, to the satoshi, posted within three days of the block's UTC date, nearest date
  first. Each entry is used once. Reversed entries (and their reversals) are left out.
. What's left falls into *On chain, not in the books* (confirmed transactions) and *In the books, not
  on chain*.

Pending transactions are listed separately. Bookie never matches them by amount and never drafts them,
because they haven't settled. The tab also compares the confirmed chain balance with the sum of the
posted entries on the bank account (*In the books*), and shows the difference.

=== Drafting and posting journal lines

For transactions that are on chain but not in the books, choose the transactions, the account for the
other side (often a suspense or clearing account you re-code later) and, for payments out, the account
for network fees. Then choose *Draft journal lines* and confirm. For each transaction, Bookie creates
lines on a new general journal batch of its own (code `BTC…`):

[cols="1,3", options="header"]
|===
| Transaction | Lines (all on the BTC bank account, amount in BTC)

| Money in | One line for the amount, balanced against the counter account
| Money out | The payment (amount less fee) against the counter account, and the fee as its own line against the fee account
| Moved within the wallet | The fee only, against the fee account
| Money out, fee not known (an input couldn't be read) | One line for the whole amount, described "fee not separated"
|===

Every line has the txid's first 35 characters as *External Document No.*, `BTC <txid>` as its
*Description* (so the next reconcile matches it by txid), the block's UTC date as *Posting Date*, and
`BTC-<first 12 characters of the txid>` as *Document No.*. Business Central takes the currency from the
bank account and converts to your local currency at its own *Currency Exchange Rates* for BTC when it
posts. Bookie doesn't set or guess a rate, so enter BTC rates in Business Central first.

Drafted lines aren't posted. They appear under *Drafted, not posted* on the Reconcile tab and as a draft
under *Manual journals*. *Post* asks for confirmation, then posts that one batch and removes it.

Before it posts, Bookie reads the chain and the books again. If a transaction in the batch has been
recorded since it was drafted (by hand, or by another draft), the batch shows *Already in the books*
with no Post button. Posting it is refused (409), so nothing is counted twice; delete that draft batch
in Business Central. A batch counts as Bookie's only if its code starts `BTC`, its name is *Bookie
Bitcoin reconcile*, and every line is on this wallet's bank account. Bookie lists and posts nothing
else, so an accountant's own `BTC...` batch is left alone. If Business Central refuses the posting (for
example, an account that doesn't allow direct posting), it posts nothing. Bookie then removes the
draft batch and says so, and you draft the lines again once that's fixed.

The person drafting and posting needs Business Central permission to create and post general journal
lines (for example `D365 JOURNALS, POST`) as well as `BOOKIE BTC READ` and `BOOKIE READ`.

=== The fiat side

Reconciling is exact on the Bitcoin side only: txid and satoshis. Bookie never matches on a fiat value
and never uses a tolerance. The fiat figures can't agree exactly. A customer pays a USD invoice in sats
worked out at the moment of payment, at their wallet's rate. Kraken's price at that minute is a little
different. Business Central converts the BTC bank entry at its own exchange rate, which it keeps one
per day. So, for a payment against an invoice:

[cols="1,3", options="header"]
|===
| Figure | Source

| The invoice amount | The invoice in Business Central
| The payment's value in the books | The BTC amount × Business Central's exchange rate for the posting date (what BC posts)
| The difference | An exchange gain or loss, posted as such by the accountant; never hidden or rounded away
| What the payment was worth at the time | Kraken at the block time (or a rate the payment provider recorded), for information only
|===

Today the Reconcile tab shows the Bitcoin side, and the wallet's transaction list shows "worth at the
time" values. Showing the invoice, the BC-rate value and the difference side by side for each payment
is planned (phase 2b in issue #4). Like everything else, it will be shown, never posted automatically.

=== Bookie's reconcile tool and API

The same reconcile, read-only, is available:

* to *Bookie in the portal* (chat and voice): the `reconcile_bitcoin_wallets` tool returns counts, the
  balance difference, and the items that need attention, in exact BTC;
* as JSON at `GET /api/orgs/{orgKey}/bitcoin/reconcile` (optionally `?wallet=<id or name>`), as the
  signed-in user, with the organisation re-checked like every portal page.

Both are read-only. Drafting and posting happen only in the portal, after the person confirms.

=== Bookie the agent

The Hermes agent has no portal session, so it looks wallets up itself with the `bitcoin` skill and
`agent/hermes/scripts/btc-wallet.mjs` (`list`, `show <wallet> [--value]`, `reconcile [<wallet>]`, JSON
output). The script reuses this code: it's bundled for Node from `web/scripts/agent-btc-wallet.ts`
with `bun run build:agent-btc` in `web/`, so rebuild and commit it when `web/src/lib/bitcoin` changes.
It reads Business Central with the agent's own service-to-service app. Give that app user
`BOOKIE BTC READ`, plus `BOOKIE READ` for reconcile; never EDIT. It reads the chain through
`BOOKIE_ELECTRUM_URL` from the agent's `config.env`, written to `~/.hermes/.env` by
`agent/deploy/04-configure-hermes.sh`. The agent accepts only `ssl://`, with the certificate checked,
or pinned with `BOOKIE_ELECTRUM_CERT_SHA256`. It never prints a descriptor or an address. When
`BOOKIE_ELECTRUM_URL` is set at install time, the scheduled weekly reconcile also reconciles the
Bitcoin wallets.

== The Electrum server

[cols="1,3"]
|===
| App setting | Meaning

| `BOOKIE_ELECTRUM_URL` | `ssl://host:port` (recommended) or `tcp://host:port`. Unset: wallets say "No Electrum server configured" and show nothing.
| `BOOKIE_ELECTRUM_TRUSTED` | `1` when the operator runs this server. Without it, Settings and every wallet page warn that the server learns every address in the wallet.
| `BOOKIE_ELECTRUM_CERT_SHA256` | Optional SHA-256 fingerprint of the server's TLS certificate, to pin a self-signed certificate instead of checking it against public CAs.
|===

Run your own server (Fulcrum, ElectrumX or electrs) next to a Bitcoin Core node where you can: an
Electrum server sees which addresses are asked about and can link them into one wallet. A public
server works but is a privacy trade-off, which is why the UI says so. Bookie never shows the server's
address in the portal. Testnet keys parse (so the BIP test vectors can be checked) but Bookie reads
mainnet wallets only.

== Demo organisation

With `BOOKIE_DEV_AUTH=demo`, Contoso Coffee Roasters has a fictional wallet, *Contoso Treasury*, read
from fixtures (`web/src/lib/bitcoin/demo.ts`). Its transaction ids are hashes of made-up labels and
its prices are labelled "Demo price (fictional)". Production refuses demo mode.
